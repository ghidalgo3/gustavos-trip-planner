# Trip overview and stays

## Overview and destinations

**Overview** is the default trip page at `/trips/{tripId}`. New trips start with an empty itinerary and an **Add destination** button. It opens a modal drawer from the right on laptops and fills the width on phones. Search for a city, select an autocomplete result, and optionally enter visit dates; the drawer does not ask for a country code. Saving closes the drawer and adds a visit to the overview, with a link to its activities. Canceling discards the draft. Overview lists visits chronologically, with undated visits last in itinerary order. Owners can delete a destination from its card after confirming that all visits and activities for that city will be removed. Overview opens activities from destination cards, flights from **Plan Flights** itinerary links, and party sharing controls from **Share** at the top right. A **Trips › Overview › current page** breadcrumb replaces trip section tabs and returns to Overview from each subpage, including while offline.

## Activity and flight navigation

Activity planning opens with destination tabs showing every visit’s dates and an Azure map centered on the selected city. The map fills the content width on phones and laptops. Activity cards below the map provide **Add activity** and card-level **Edit** actions. Both open a drawer; new activities use manual entry and Azure Maps place lookup. Destination tabs share a scroll position. Considering, Planned, and Not Interested display the stored Maybe, Yes, and No planning decisions, respectively. Each activity in the Ideas list has a dropdown showing its current status, with Considering (bookmark), Planned (calendar-check), Not Interested (minus-circle), and Remove (trash) options; the same menu is available in map details. Deletion requires confirmation. Read-only members see the state without editing controls. Activities have separate Description and Notes fields: Description explains the activity itself; Notes holds planner-written scheduling details, reminders, and other related information. Both support up to 10,000 characters, grow with their text in the drawer, and are saved with the complete activity. Notes remain visible in read-only details and travel with the exported trip document; they do not enforce scheduling rules. Activities support user-managed URL/label links for details, bookings, or tickets, editable in the activity drawer. Overview cards show activity counts by state, or **Plan Activities** when empty. Narrow flight cards connect the profile’s home city to the first destination, each chronological visit to the next, and the final destination back home. They show matching selected flight numbers (including connections) or **Plan Flights**, linking to the existing flight planner at `/trips/{tripId}/flights`. Located activity cards offer **Open in Maps**, using Apple Maps links on Apple devices and Google Maps links elsewhere, with browser fallback.

## Visit dates and overlap validation

Destination creation and visit-date editing are on Overview. A single inline calendar selects arrival and departure as a range and highlights other cities’ stays, including repeat visits, with a color legend below the month. Visits can share an arrival/departure day (for example, June 10–15 followed by June 15–20), but cannot overlap inside another visit. The calendar blocks conflicting selections, including ranges spanning another visit; REST and MCP reject conflicting date writes with `409 destination_dates_overlap`. Editing excludes only the current visit, not every visit to its city. PostgreSQL serializes date checks and writes per trip to prevent simultaneous edits from creating overlaps. Map loading and failures are visible, with a retry that fetches a fresh SAS token. **Activities** remains available at `/trips/{tripId}/activities`; flights, stays, and plans are no longer navigation tabs in this first design pass. Trip-wide dates and flexibility controls will follow. The **Choose stay** drawer searches Maps by hotel name or address. Users select a pin to save the accommodation for that visit.

## Destination API

`GET /trips/{tripId}/destinations` returns an `application/geo+json` FeatureCollection, empty for a new trip. `POST` to the same route accepts a destination GeoJSON Feature with required Point coordinates from the selected autocomplete result and properties `name`, `countryCode`, optional object `constraints`, and optional `arrivalDate` and `departureDate`. The country code remains API metadata rather than a form field. `PUT /trips/{tripId}/destinations/{destinationCity}/stays/{stayId}` replaces its optional dates; `DELETE` removes the visit. `?includeInactive=true` includes cached past cities. `GET /trips/{tripId}/destinations/{destinationCity}` returns a city Feature. Under that city, `GET` and `POST /activities` list and create complete activity Features, and `GET`, `PUT`, and `DELETE /activities/{activityId}` read, replace, and remove one. Activity writes require the city's `contextVersion` in `Destination-Context`; replacements and deletes also require the current activity ETag in `If-Match`.

## Stay selection and visit dates

See [transportation and hotel resources](transportation.md#hotel-and-airport-references) for how hotel records relate to stays.

Place searches in activity and stay drawers share numbered full-width result buttons, name/address typography, and loading placeholders. Stay search results appear as matching numbered pins in the drawer map; selecting a result or its pin saves the same stay location.

Destination accommodation is managed with the stay button on each visit card on Overview. Repeat visits to the same city have independent accommodations. `GET`/`PUT`/`DELETE /trips/{tripId}/destinations/{destinationCity}/stays/{stayId}/location` reads, replaces, or removes that visit's accommodation; PUT accepts a GeoJSON Point Feature with `properties.name`. Destination Features return it as `properties.stays[].stayLocation`. Each visit's accommodation appears as a distinct house marker on the activity map. Owners and Planners can change it; Travellers can view it. The evaluator, route enrichment, and solver use the correct visit's hotel for the day's outbound and return travel; a visit without a hotel keeps the existing open-route behavior. Changing accommodation invalidates the planning input context without moving saved calendar events. MCP exposes `get_visit_stay_location`, `replace_visit_stay_location`, and `delete_visit_stay_location` with the same authorization and validation as REST. Address research remains a city-scoped preview; saving the chosen result always requires a visit ID.

Each saved accommodation has visit-specific `properties.checkInTime` and `properties.checkOutTime` ISO local clocks (`HH:mm:ss`), defaulting to `16:00:00` and `11:00:00`. The stay drawer's **Details** section edits both in a draft and saves the complete accommodation resource, preserving the selected hotel. These times are stored on the visit's accommodation selection, survive portable documents and offline hydration, and appear as check-in/check-out events on the visit's arrival/departure dates in Schedule. Repeat visits to the same hotel can use different times. Migration `0023_StayCheckInOutTimes.sql` adds and defaults the two clocks for existing selections. The existing `replace_visit_stay_location` MCP tool accepts the same clocks.

Changing either date of a visit atomically unschedules activities assigned to that visit and clears their fixed dates/times, its saved day settings and availability choices, and its dated travel overrides. Activities retain their decision states, durations, and preferences and can be scheduled again. Other visits, including repeat visits to the same destination, retain their schedules. Saving unchanged dates or rejecting an invalid date change leaves schedules intact; old plan versions cannot restore invalidated assignments.

Migration `0015_VisitStayLocations.sql` copies each old city-wide accommodation onto all of its existing visits, preserving current choices while allowing independent edits afterwards. New visits start with no accommodation, and deleting a visit cascades only to its own accommodation. The old city-wide `/stay` read/write routes are replaced by the visit-specific resource so clients cannot accidentally update all visits.
