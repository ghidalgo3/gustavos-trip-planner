# Evaluating the evidence

Prioritize cognitive load, navigation, number of actions, discoverability, consistency, product design guidelines, then accessibility and responsive usability. Use `list` to load rule records and apply their scope and documented exceptions. The [heuristic library](heuristics/core.yaml) links to primary references. Apply Nielsen and Shneiderman to interaction behavior, Gerhardt-Powals and recognition rather than recall to information demands, and Cognitive Walkthrough to each decision. Use Interaction Cost and GOMS/KLM when comparing successful paths. Hick's Law, Fitts's Law, and Gestalt principles guide inspection where options, target acquisition, or grouping affect a task. Record the exact WCAG criterion for a verified accessibility finding and the relevant platform or product guideline for a convention.

One successful input dispatch counts as one logical action, including clicks, taps, text-entry sequences, individual key commands, wheel movements, gestures and browser back. Record each separately. Character counts and key command counts are synthetic input data. A drag is one gesture. Loading, observations and setup do not count. Page transitions are changes in visible URL paths and route depth is the count of path segments. Modal transitions are changes in observed modal state. Label task-specific area switches, decisions, memory demands, and truly unnecessary backtracking when supported by the trace. Timing from the agent session does not establish human cognitive workload.

Use success evidence to identify the shortest verified completed attempt. Efficiency equals shortest verified actions divided by observed actions. Excess equals observed actions minus shortest verified actions. Overhead equals excess divided by shortest verified actions. An undefined ratio is null. A regression delta is the current value minus the baseline value for comparable runs. Compare across viewports in the narrative using equivalent journeys and inspect the evidence behind the differences.

Create an assessment JSON with `findings`, `positives`, `limitations`, and `untested` arrays. Each item in `findings` follows [finding.schema.json](../schemas/finding.schema.json). Link screenshot state IDs such as `observed-s2` from the same journey. Write reproducible steps, remediation that an implementer can execute, and what it should improve. Use a stable ID based on the underlying problem, independent of version or screenshot. Classify the claim as observed, inferred, or hypothesis. Cite observations for observed and inferred claims. Keep an unverified hypothesis low confidence. Review previously flagged issues in current evidence before calling them resolved.

Severity ranges from 0 (observation) to 4 (a critical task is blocked or has a similarly severe consequence). Assign 1 for minor friction, 2 for moderate disruption, and 3 for major disruption or a problem needing a substantial workaround. Explain severity in terms of impact, frequency or persistence when evidence permits. Confidence reflects the quality and reproducibility of evidence. A positive entry uses `scenarioId`, `description`, and `evidence`. Record unavailable profiles, incomplete checks, and skipped journeys explicitly. Browser measurements cover individual checks and tested states. For qualitative findings with visual evidence, inspect whether the cited screenshot clearly shows the issue.
